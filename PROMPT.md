# Standalone prompt

Copy the prompt below into an agent working in your project. It does not require the skill or access to this repository. To assess a specific change instead of setting up the system, replace the first sentence with: “Assess the documentation impact of my current change; update only what is necessary.”

```text
Set up or improve an agent-friendly living documentation system for this project, and give future agents a concise way to maintain it. Follow my instructions, the project's conventions, and the permissions available to you.

If I requested only an assessment or maintenance, use the existing map and sources without starting an unsolicited setup, renaming files or creating base files just to satisfy the setup procedure. Report structural gaps separately.

First inspect the relevant agent instructions, existing documentation, structure, code, configuration, and tests. Read selectively. Identify existing sources of truth, gaps, and conflicts. Distinguish implemented behavior from intended behavior and plans. Investigate discrepancies; report unresolved ones and ask me when a product or architectural decision is needed. Do not invent facts or decisions.

Preserve useful content and existing local changes. Use the project's language. During setup or an explicitly requested reorganization, establish these base files for every profile:

- Root AGENTS.md, or existing CLAUDE.md: state that documentation exists, point to docs/index.md and give the maintenance workflow. Preserve existing instructions; both files are not required. If both exist, keep documentation pointers consistent.
- docs/index.md: index all project documentation, including sources outside docs/, with real links, short descriptions, audiences, reading triggers and current/planned/historical status.
- docs/product.md: purpose, users or consumers, problem, scope, capabilities, main workflows, rules and limitations. Separate current behavior from future plans.
- docs/architecture.md: technical structure, component responsibilities, dependencies, integrations, important boundaries and failure behavior. Link to separate module documents for detail; use docs/modules/<module>.md by default when the detail needs its own home.

Conditionally require docs/database.md at any profile when the repository owns or manages a database, its schema or migrations, or directly accesses a shared database with important data contracts. Inspect actual schemas, migrations and read/write flows; a database dependency alone is not evidence. Cover database purpose and ownership, main entities and relationships, invariants, lifecycle, access and migration constraints. Link to authoritative schemas and migrations for exact fields and to operations procedures rather than duplicating them. For shared databases, link to the owner's documentation and describe only this repository's usage. Link the document from architecture and the index. Repositories without a database role, including documentation-only projects, API-only frontends and stateless tools, do not need it. Files, caches or logs alone do not justify it; retain any important non-database data rules in the appropriate source. Explain omission briefly in the setup report or architecture, without creating an empty file or linking to a missing one. During setup or requested reorganization, apply the same preservation, rename and reference-repair rules below to an equivalent database document.

Rename an existing source with the same role and boundaries to the standard path and repair links and instruction references. Split multipurpose sources into the appropriate homes while retaining other useful content. Reconcile an existing destination without overwriting local changes; ask when competing sources require an intent decision. Keep specialized sources in place and link to them instead of copying their details. Flag external references you cannot update. Do not archive or delete useful material merely to fit the structure.

Document only evidence-backed knowledge useful to this project; avoid empty templates or duplicating details reliably expressed by code, schemas or tests. Profiles control depth and additional coverage, not whether the base files exist. Mark unknowns and missing evidence rather than inventing content. Keep current behavior and constraints distinct from durable decisions and their rationale, plans and their status, and historical material. Use Git for complete history when available. Keep useful legacy records labeled as historical, and preserve superseded decisions.

Add a short maintenance instruction for future agents: read the index and relevant sources before work; after a meaningful change, assess the impact on documentation and make the smallest accurate update to the appropriate source. Keep the index complete when documents are added, renamed, removed or change status. Create decisions or plans only when justified. If meaning has not changed, no documentation update is needed. Do not impose a new commit, approval, or other project workflow. Tell me if my agent needs a manual step to discover the instructions.

Select a documentation profile after inspecting the project; report your recommendation, concrete evidence, applicable conditions and uncertainties. Light suits a small cohesive project with few workflows and limited operational or coordination needs. Standard suits meaningful workflows, data or operational concerns, or several significant components, including monoliths. Heavy suits consequential contracts among services, repositories, independently evolving modules or owners; repository count alone is insufficient. A modular monolith needs meaningful module responsibilities, dependency direction and contracts where code alone is insufficient. Reassess when coordination, ownership or risk materially changes. Individual repositories may have different profiles from the system as a whole.

Required coverage for every profile: the base files above with evidence-backed content, concise for light projects. Standard requires deeper product/service workflows and rules and architecture coverage of components, dependencies, integrations, trust boundaries and important failure behavior. Heavy additionally requires a map of owners, producers and consumers, authoritative shared contracts, compatibility dependencies and how changes are verified. Additional topics may share a document when their boundaries remain clear; product and architecture retain their separate base files. For each additional document explain its audience, purpose and why existing sources are insufficient.

Required when applicable: data ownership, lifecycle, invariants and migration constraints when persistent state matters, linking to the schema for exact fields; operations prerequisites, safe procedures, verification and recovery when non-obvious; decision records with context, choice, known rationale, consequences and status when durable choices could be costly to reverse; initiative plans with status, scope, dependencies, milestones and verification for long-running work; domain/module notes when broad documents cannot explain a recurring complex boundary; labeled historical sources when useful. Keep superseded decisions and links to successors. Business, design and other material is optional when it serves a real audience or recurring task.

For an existing project: inspect status, instructions, documentation and repository boundaries; trace representative workflows through code, tests, schema and configuration; inventory covered, missing, conditional and unknown knowledge; classify discrepancies as stale documentation, possible defect, intentional divergence or unresolved. Ask when intent needs a decision. Establish the map, agent instructions and evidence-backed current state first, then applicable conditional and cross-repository coverage. Preserve legacy information until it has a confirmed home. Identify inaccessible sources and do not assert unverified behavior.

Consider the user's actual recurring workflows, agent platform and existing skills before recommending any project skills. Recommend only skills that solve a real repeated or fragile task better than existing instructions or skills; explain the trigger, benefit and alternative. Examples when justified include documentation-impact assessment and cross-repository contract maintenance. No extra skills is a valid result. If I request or authorize tailored skills, create only the selected skills in a supported project location within scope, with valid metadata, narrow triggers, concrete steps, source links and verification; explain invocation and discovery. Preserve existing skills; do not install user-wide or change configuration without authorization. Ask about platform or location only when necessary.

For maintenance, read relevant sources and code, then assess product, architecture, data, operations, decisions and initiative context after each meaningful task. Update docs/database.md or the existing equivalent source when its ownership, entities, relationships, invariants, lifecycle, access or migration constraints change. If the change first introduces a database role, assess the conditional document within the requested scope without starting a full migration. Update affected owners and map pointers within authorized scope; report exact cross-repository follow-up when blocked. An access-rule change may affect product and data; a changed shared contract requires owner and consumer checks; a replaced decision needs a successor and retained history; an internal refactor preserving semantics may require no document change, with the reason reported. Plans are not current truth, permission to begin work or task diaries.

Verify changed links and paths, accuracy against inspected evidence, preservation of existing material, and justified duplication. Review the diff for credentials, personal data, and other information inappropriate for its destination. Report changes, no-op decisions, unresolved conflicts, and verification limits without exposing sensitive findings.
```
